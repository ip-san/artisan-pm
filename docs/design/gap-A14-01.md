# A14-01 設計メモ: 多言語対応

状態: `blocked(要承認)`。全 UI 文字列に触れる規模 L の変更で、翻訳資産の作り方に判断が要る。

## 背景

Redmine は `config/locales/*.yml`(49 言語)、`default_language`、`force_default_language_for_anonymous`/`_for_loggedin`、ユーザーの `language` で表示言語を決める。本アプリは Blade/PHP に日本語を直接書いており、`lang/` ディレクトリが無い。`users.language` 列はあるが UI で使われていない。

## 選択肢

1. **A. Laravel 標準(`__()` と `lang/{ja,en}.json`)を段階導入(推奨)**: キーは日本語原文(JSON の「原文 → 訳」形式)。既存の日本語文字列を `__('原文')` で包むだけで、原文が既定言語(ja)のまま動き、`en.json` に訳を足した分だけ英語になる。
   - 長所: 置換が機械的で、未翻訳は原文にフォールバックして壊れない。画面群ごとに段階的に進められる。
   - 短所: 原文が変わると訳のキーも変わる。文中に変数が入る文の切り出しが要る。
2. **B. 意味キー(`messages.issue.subject`)を全部定義**: 訳の管理は堅いが、置換と初期定義のコストが大きい。
3. **C. Redmine の `ja.yml` のキーを流用**: 翻訳作業は減るが、Redmine のキー体系に本アプリの文言を合わせる必要があり、文言が食い違う。

## 判断が要る点

1. 方式(推奨 A)と、最初に用意する言語(ja + en の 2 言語)。
2. 範囲: 画面(Blade/Volt)、メール、PDF、CSV の見出し、バリデーション文言、enum の `label()`、定数配列のラベル(`DISPLAY_COLUMNS` など)。範囲を段階に分ける(画面 → メール → PDF/CSV)。
3. 言語決定の順序: ユーザーの言語 → `force_default_language_*` → 設定 `default_language`。`SetLocale` ミドルウェア、`Carbon::locale()`、日付/数値の整形(A4-12 と連動)。
4. 既存テストは日本語文字列を assert しているため、既定言語(ja)を変えない限り影響しない。

## 推奨案と分割

1. **A14-01a**(S): `SetLocale` ミドルウェア、ユーザー言語の選択 UI、設定 `default_language`、`lang/ja.json` と `lang/en.json` の雛形。
2. **A14-01b〜**(M×n): 画面群ごとの `__()` 置換と英訳(課題 → プロジェクト → 工数 → Wiki → 管理画面 …)、続いてメール、PDF/CSV、enum ラベル。

## 影響範囲

`resources/views/**`、`app/Enums/*::label()`、メールテンプレート、`bootstrap/app.php`(ミドルウェア)、設定、プロフィール。
