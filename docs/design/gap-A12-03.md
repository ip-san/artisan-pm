# A12-03 設計メモ: プラグインのランタイム検出

状態: `blocked(要承認)`。プロジェクトの規約で「承認なしに新しいベースフォルダを作らない」とあり、この機能は `plugins/` という新しいトップレベルのフォルダを前提にする。また、ディスク上のコードを実行時に読み込む安全境界の判断が要る。

## 背景

Redmine は `plugins/*/init.rb` を起動時に走査して読み込む(`Redmine::PluginLoader`)。本アプリのプラグインは `bootstrap/providers.php` に ServiceProvider を手動登録し、`PluginManager`(`app/Support/Plugins/PluginManager.php`)に権限・アクティビティ・ダッシュボードブロック・カスタムフィールド形式・メニュー・ビューフックを登録する。バージョン要件の検査と設定 UI は実装済み。

## 選択肢

1. **A. `plugins/<名前>/plugin.json` を走査(推奨)**: マニフェストに `id`、`provider`(ServiceProvider の FQCN)、`autoload`(PSR-4 の名前空間 → 相対ディレクトリ)を書く。`PluginServiceProvider` が起動時に走査し、`autoload` を `spl_autoload_register` で登録して `$app->register($provider)` する。
   - 長所: Composer の再実行が要らず、Redmine と同じ「フォルダを置くだけ」。
   - 短所: 新規トップレベルフォルダ `plugins/`。Composer の autoload 最適化(`--classmap-authoritative`)下では動的登録が効くか確認が要る。
2. **B. Composer パッケージとして配布(`extra.laravel.providers` による Laravel の自動検出)**: 新フォルダなし、既存の仕組みだけで動く。ただし Composer 依存の追加(承認事項)になり、「置くだけ」ではない。
3. **C. 既存の手動登録のまま**: 現状。ギャップは残る。

## 判断が要る点

1. 新規フォルダ `plugins/` を作ってよいか(A の前提)。`.gitignore` に入れるか(プラグインをリポジトリ外に置く運用か)。
2. **安全境界**: 走査対象は運用者が管理するファイルシステム上のコードで、管理画面からのアップロードは受け付けない(推奨)。読み込むのは有効化されたプラグインだけにし、既定は「無効」(管理画面で有効化するまで読み込まない)。
3. 有効/無効フラグの保存先: `settings` の `plugins_enabled`(ID の配列。推奨)。無効化したプラグインの権限やレジストリ登録は消え、ロールに付与済みの権限キーは残るが無視される。
4. マニフェストのバージョン要件(`requires_app_version`)を、既にある `PluginRequirementException` の検査につなぐこと。

## 推奨案と分割

1. **A12-03a**(S): マニフェストの読み取りと検証(`PluginDiscovery`)、autoload 登録、`PluginServiceProvider` への接続。既定は無効。
2. **A12-03b**(S): `/plugins` 管理画面に有効/無効の切替と、読み込み失敗(マニフェスト不正・要件不一致)の表示。

## 影響範囲

`app/Providers/PluginServiceProvider.php`、`app/Support/Plugins/`、`resources/views/livewire/plugins/`、設定(`plugins_enabled`)、`.gitignore`。既存テスト `tests/Feature/Plugins/*` は手動登録の経路を使い続けるため影響なし。
