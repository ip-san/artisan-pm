# A4-12 / A14-02 設計メモ: ユーザーのタイムゾーンと日付・時刻の表示形式

状態: `blocked(要承認)`。表示側の約 120 箇所に触れる横断変更で、方式の選択が要る。バックログも A14-01(多言語化)との同時実施を勧めている。

## 背景

Redmine は `users.time_zone`(個人)と設定 `default_users_time_zone`、表示形式の設定 `date_format` / `time_format` / `timespan_format`(工数の「1:30」か「1.50」か)を持つ。本アプリはアプリ全体で `config('app.timezone') = 'UTC'` の単一設定で、日時は Blade 内の `->format('Y-m-d H:i')`(30 箇所)、日付は `->format('Y-m-d')`(34 箇所)/`->toDateString()`(57 箇所)で直接整形している。

## 選択肢

1. **A. 整形ヘルパーに集約(推奨)**: `App\Support\Format\DateTimes`(`date()` / `dateTime()`)を作り、表示側をすべてこれ経由にする。ヘルパーがユーザーのタイムゾーンと設定の形式を解決する。保存は UTC のまま。
   - 長所: 変更が表示層に限られ、DB の値が変わらない。テストで固定しやすい。
   - 短所: 約 120 箇所の置換が要り、取りこぼすと形式が混在する。
2. **B. リクエストごとに `date_default_timezone_set` / Carbon の既定を切り替える**: ミドルウェアでユーザーのタイムゾーンを設定する。
   - 長所: 置換が要らない。
   - 短所: Carbon の解釈が全域で変わるため、期限・スケジュール計算・キューのジョブが誤ったゾーンで動く危険。日付のみの列(期日、作業日)は影響しないが、`now()` を使う比較が全部ずれる。
3. **C. 形式だけ実装し、タイムゾーンは対象外**: 影響が小さいが A4-12 の主目的を満たさない。

## 判断が要る点

1. 方式(推奨 A)。
2. **日付のみの列**(`start_date`、`due_date`、`spent_on`)はタイムゾーンで動かさない(Redmine も同様)。日時の列(`created_at` 等)だけ変換する、でよいか。
3. 入力側: フォームの日時入力(現状ほぼ日付のみ)の扱い。工数の日付は「ユーザーの今日」で既定値を決める(`now()` をユーザーのゾーンで)必要がある。
4. 既定値: `default_users_time_zone` は空(=サーバー設定 UTC)、日付形式は現行の `Y-m-d`(ISO)を既定にして既存の見た目を変えない。
5. API は ISO 8601 の UTC のまま(表示形式の設定は API に影響させない)。
6. 工数の `timespan_format`(小数 / 時:分)は既に `App\Support\Format\Hours` があるため、そこへ設定を足す。

## 推奨案と分割

1. **A4-12a**(S): ユーザー列 `time_zone`、設定 `default_users_time_zone`、プロフィールの選択、`DateTimes` ヘルパー(テスト付き)。
2. **A4-12b**(M): 表示層の置換(日時 → 日付の順、画面群ごとに分けてコミット)。
3. **A4-12c**(S): 日付形式・時刻形式・時間形式の設定とヘルパーへの反映(A14-01 のロケール対応と合わせる)。

## 影響範囲

`resources/views/**`(表示側約 120 箇所)、PDF/CSV/Atom の日時、メール本文の日時、`Hours`、設定画面、プロフィール。テスト側で日時文字列を固定している既存テストは、ユーザーのタイムゾーンが空(UTC)の間は変わらない。
