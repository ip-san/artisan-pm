# A12-06c 設計メモ: メールからのアカウント自動作成(`unknown_user`)と関連オプション

状態: `blocked(要承認)`。認証されていない差出人のアドレスからアカウントを作る、セキュリティ判断を含む変更。

## 背景

Redmine の受信メール(`MailHandler`)には差出人が未登録のときのオプションがある。

- `unknown_user`: `ignore`(既定、メールを捨てる)/ `accept`(匿名として受け付ける)/ `create`(アカウントを作る)。
- `no_permission_check`: 差出人の権限を確認しない。
- `default_group`: `create` で作ったユーザーを入れるグループ。
- `no_account_notice`: 作ったアカウントの案内メールを送らない。
- `no_notification`: 受け付けたメールの結果として通知メールを送らない。

本アプリは A12-06(2026-09-20)までに、差出人が既存のユーザー(主アドレスまたは追加アドレス)で、かつ権限があるときだけ受け付ける(`unknown_user=ignore` 相当)。`From:` ヘッダは詐称できるため、未登録の差出人を信用して課題を作る経路は意図的に作っていない(`IncomingMailService` の冒頭コメント)。

## 選択肢

1. **A. 何もしない(推奨)**: `unknown_user` を実装しない。5 つのオプションのうち `default_group`/`no_account_notice` は `create` が前提のため不要になり、`no_permission_check` と `no_notification` だけが残る。
2. **B. `create` だけ実装**: 未登録の差出人に自動でアカウントを作り、`default_group` に入れ、案内メールを送る。差出人の検証は無い(SPF/DKIM は見ない)ため、任意のアドレスでアカウントを作れる。実装するなら、登録モード(`self_registration`)の設定に従い、メール確認済みとして扱わず、案内メールのリンクでの有効化を必須にする。
3. **C. `accept` だけ実装**: 匿名ユーザーとして受け付け、匿名で課題を追加できるプロジェクトだけに作る。

## 判断が要る点

1. A(実装しない)でよいか。B/C にするなら、差出人の詐称をどう防ぐか(受信サーバー側の SPF/DKIM 検証を前提とする、専用の共有キーが付いた `POST /mail_handler` だけで許す、など)。
2. `no_notification` は差出人の判断に関係なく単独で意味があるため、A の場合でも別に実装するか(受信メールの処理中だけ通知イベントを止める)。

## 推奨案と分割

- **A12-06c(本行)は実装せず `blocked` のまま**にし、承認されたら B か C を選ぶ。
- A を選ぶ場合の残りは **A12-06d**(S): `no_notification`(受信メールで作った課題・更新の通知を送らない設定)。
